Product philosophy

把优秀实践，变成少数明确的规则。

已有项目解决了各自的复杂问题。ArkCode 保留与首版编码任务直接相关的机制，并按 SDK 的所有权重新设计。

从 Codex 的执行快照出发

一次运行，使用明确的设置。

启动时固定项目、模型、工具集合和权限模式。运行中设置不可热改，用户停止后再切换。

用整个运行的快照满足首版需求，暂不建立完整 StepContext 系统。C03

从 Kimi 的状态与事件出发

界面反映实际状态。

批准等待、重试、压缩、停止中都有明确显示。窗口刷新先取状态快照，再接收增量。

只保留本地实例的 epoch 和序号，暂不建设持久事件回放服务。K06K24

从 ZCode 的命令准入出发

一次提交，只启动一次。

重复点击使用同一个 commandId。一个工作区同时只允许一个编码运行，旧实例的批准不能放行新工具。

在本地控制入口落实去重与状态校验，暂不复制工作流引擎。Z02

从 Pi 的会话权威出发

让 SDK 继续拥有会话。

会话树、模型上下文、压缩和重试由 SDK 管理。ArkCode 消费事件，并补充产品规则。

聊天记录只有 Pi 一份权威存储，避免第二份 messages 数据库。A01A06

产品承诺。 用户始终能回答四个问题：它正在做什么、需要我允许什么、已经改了什么、哪些结果经过验证。首版的复杂度预算优先花在这四件事上。

以本地桌面工作台为建议形态。保留代码审阅和外部编辑器入口，首版无需同时打造完整 IDE、CLI 和云服务。

System architecture · proposed

一个本地应用，四处明确的责任。

建议使用 Electron 与 React/TypeScript。一个受监督的 Node 执行进程承载 SDK。进程边界用于隔离阻塞和故障，文件与命令权限仍需单独控制。

这一个额外进程的理由。 执行进程异常退出或阻塞时，窗口仍能呈现中断状态。代价是一套有限 IPC、进程监督和取消验收。首版只有一个执行进程，不增加后台守护服务、WebSocket 或进程池。Electron 提供此进程模型，具体隔离效果仍须故障注入验证。Electron 进程文档
比较过的另一种形态：让 SDK 与桌面主进程同进程

同进程更省装配代码，适合先做最小技术切片。最终首版建议保留独立执行进程，因为“停止和故障时仍有可操作界面”属于编码工作台的核心体验。吸收同进程方案的范围约束：只有内置可信扩展、运行中输入只存草稿、整次运行固定设置。

这是基于责任边界的设计选择，尚未测量两种方案的开发成本。后续不因远端服务或多代理的可能性提前扩张协议。

State ownership

每类事实，只设一个写入者。

先回答谁拥有状态，再决定放在哪个文件。首版用 Pi JSONL 与少量 ArkCode sidecar；没有额外数据库或事件溯源平台。

数据唯一拥有者保存方式恢复与边界
会话、消息、分支与压缩Pi SessionManager独立 ArkCode 数据目录中的 Pi JSONL通过 SDK 打开。UI 的消息视图是可重建投影。A01A04
工作区偏好与会话索引桌面宿主小型 JSON 元数据，临时文件后替换索引从会话文件校准。替换失败显式报错，不把内存修改当已保存。
运行收据与批准记录运行控制每次 run 的 sidecar，含状态、标识与工件引用运行前写 started 标记，结束写结果。它不是第二份聊天历史，也不与 Pi 跨文件原子提交。
文件基线与命令输出审阅模块按 runId 保存文件或引用，设置体积上限超限、二进制、无法读取的范围明确标记。缺失证据不推断成功。
待审批请求与运行中草稿审批属于执行进程；草稿属于 UI批准等待只在当前 epoch 有效；草稿单独保存重启后旧批准失效。草稿不会自动变成新一次提交。
凭据桌面宿主的凭据适配器使用系统凭据保护能力输入只向宿主提交；保存后 UI 只读配置状态。密钥按需传给执行进程，不回显到会话或日志。

同一目录，只有一个运行占用。

宿主按真实目录识别工作区。所有会话共享它的运行槽。首版单实例，禁止第二个可写 AgentSession 打开同一会话文件。不同会话可以浏览，执行切换必须等当前运行结束。

历史恢复与执行恢复分开。

sidecar 显示未结束，或与 Pi 历史不一致时，统一标为“上次运行中断”。先确认上一实例的受管命令已经退出，再检查工作目录并接受新指令。无法确认时只读恢复历史，保持执行锁。Pi 的协议补齐不代表命令副作用已恢复。A11

首版承诺可恢复已保存的会话，不承诺每个流式字符都已落盘、断电零丢失或命令 exactly-once。A04A05

Run lifecycle

运行状态与任务结果，分别说明。

“现在空闲”只说明没有继续执行。“验证通过”需要执行证据。重试、压缩和工具错误可以发生在同一次运行里。

ArkCode 提案接口 · 不是 SDK 原生 API
openWorkspace(path) → workspaceSnapshot
openSession(sessionId) → sessionSnapshot
submit({ epoch, commandId, sessionId, text })
  → accepted(runId) | busy | stale
decideApproval({ epoch, runId, approvalId, choice })
  → accepted | stale
stop({ epoch, runId }) → stopping | alreadyIdle
getSnapshot() → workspace + session + activeRun
subscribe() → ordered view events

运行中输入留作草稿。
v1 不提供 steer、follow-up 或自己的消息队列。
切换会话后重新绑定 SDK 订阅。
  • 区分传输接收与执行完成accepted 表示本实例受理。相同 commandId 返回同一受理结果；进程重启后先读快照，不自动重发。
  • 旧事件不能进入新会话事件带 epoch、sessionId、runId、seq。失配即丢弃，序号缺口时重新取快照。UI 重载不启动新的 AgentSession。
  • 终态以 SDK settle 为基础agent_end 不能释放运行槽。agent_settled 或已收敛的异常路径之后，再确认工具清理、记录结果并释放占用。A06
  • 停止有完成条件停止新准入，撤销审批等待，处理队列，调用 abort 并核对命令退出。无法确认时显示“停止未确认”，保持工作区占用。A07A09
为什么首版不做运行中补充与排队？

Pi 已提供 steer 和 follow-up，但它们有不同交付时机，未交付输入也不自动获得持久恢复保证。首版采用“草稿 + 停止后发送”，使用户能清楚判断哪句话已进入当前任务。后续有明确需求再直接适配 SDK 队列。A08A10

Trust & tools

授权针对具体动作，并在执行端生效。

默认协作方式是“项目内编辑，命令逐次批准”。另提供“仅查看”，只暴露文件读取和检索工具。工具集合明确列出。

动作首版规则用户看到什么
读取与检索限定选定工作区，敏感文件遵循拒绝清单。仅查看模式不提供 shell。正在读取的文件和检索范围，可展开详情。
edit / write本次运行已授权的项目路径内可执行。规范化路径，处理链接，拒绝越界和 Git 内部目录写入。运行前范围提示，写入后的逐文件变化。不能把路径检查宣传为 OS 隔离。
shell / 测试脚本逐次确认最终命令、cwd 与 shell。批准只适用于当前调用；失败不自动扩大权限。“在你的电脑上执行，具有当前用户权限。”显示准确命令，允许这一次或拒绝。
扩展与项目代码v1 仅装配自有可信扩展；不自动执行仓库扩展、脚本 hook 或用户 Pi 全局扩展。可以查看所载入的文本指令来源。打开目录不会默认为第三方代码执行授权。

审批等待由 ArkCode 管理。

自有 tool_call 扩展把请求交给审批 broker。UI 发送用户决策，broker 校验运行身份并结束等待。无 UI 的 SDK 不会替产品自动弹出批准框。A12A14

用户点击停止时，broker 必须主动结束挂起的 Promise，随后 SDK 的 abort 才能完成。旧卡片的“允许”只能返回失效。A07

扩展信任必须先于加载。

提供受控 ResourceLoader，显式配置 agentDir、cwd、设置与工具。避免默认项目 trusted 及自动发现代码改变产品行为。加载完成后的 extensionsOverride 不构成安全过滤。A03A16A17A18

工具参数可被 hook 修改。因此只加载自有可信处理器，批准后校验最终参数摘要，禁止后续处理器悄悄改变执行对象。A13

批准与隔离的边界。 已批准的 shell 可以执行任意当前用户可执行的代码，测试脚本也可能联网或写文件。首版不提供 OS 沙箱保证。执行进程隔离主要解决应用故障；受限 IPC 和 renderer 隔离保护界面权限边界。Electron 安全文档
Changes & verification

审阅的是实际文件，结论要带证据。

默认在用户当前工作目录直接修改。第一次运行前明确这一点，并展示已有 staged、unstaged 和 untracked 修改。

开始时记录基线

保存 Git HEAD、index 状态及纳入范围的已有脏文件内容。干净的跟踪文件可用 Git blob 作为基线；未跟踪文件需保存可用的运行前内容。

大型、二进制、忽略或不可读文件标为未覆盖。无 Git 时只保证受控文件工具的前后快照。

展示两种不同差异

“工作区相对 Git”说明当前全部变化。“运行期间变化”说明本次开始前后的差别。后者可能混入外部编辑器修改。

工具前后哈希能证明某次 ArkCode 写入，不能证明最终整份 diff 全由 Agent 产生。

验证绑定实际执行

验证记录包含命令、cwd、shell、退出码、输出与发生时间。执行成功只证明该命令成功，不宣称整个项目正确。

测试后继续改动相关文件时，验证标记为可能过期，提示重新运行。首版可保守地在任意后续文件变化时置为过期。

测试通过展示实际命令的 exit 0 与输出；注明检查范围。
测试失败 / 未执行展示失败原因或批准被拒。文件变化仍保留。
中断 / 来源混合指出哪些副作用或文件归属未知，邀请用户检查。
首版的接手动作。 查看差异、打开文件、打开外部编辑器、复制补丁、继续提出修改。暂不提供一键回滚、自动 stash、reset 或提交。审阅完成不会再应用一次已写入的变更。
Context without a second harness

会话、项目指令、压缩与缓存各有职责。第一版不把它们统一包装成一个含义模糊的“记忆系统”。

一个应用、一份契约、一个活动执行进程。
会话不另建通用 AgentEngine 接口。
SDK 版本固定，升级先跑行为契约。

最少的核心对象

  • Workspace规范化真实目录、工具策略与运行占用。首版同一时刻只有一个活动工作区。
  • SessionPi 会话标识与文件引用。ArkCode 的标题、排序等索引可重建。
  • Run一次 submit 到 SDK settle 与清理完成。包含多个模型回合、工具、压缩与重试。
  • Approval绑定执行实例、运行、调用、cwd 与参数摘要的单次决策。
  • ReviewEvidence文件基线、运行期间差异和命令结果。它不代替聊天历史。

接入 SDK 的具体约束

显式提供 cwd、独立 agentDir、设置、受控资源加载器与工具集合。注册唯一审批扩展，在 prompt 前显式设置 session.agent.toolExecution = "sequential"，完成订阅后再运行。工具串行是 ArkCode 的配置，SDK 默认是 parallel。A21切换会话时解绑旧订阅，dispose 旧实例，再绑定新实例。A02A03A19

SDK 默认工具包含 bash。Windows 的 shell 必须显式选择，并在非 ASCII 路径下验收。MCP、codemode 和 tool_search 不纳入本版默认集合。

把复杂度放在可验收的边界

IPC 入口校验数据，UI 不能传任意 shell 绕过工具批准。工具输出作为数据渲染，Markdown 不执行原始 HTML。文件打开入口校验路径，外链交给系统浏览器。

初次配置凭据由设置界面提交给宿主，日志脱敏。SDK 或 provider 的错误保留诊断标识，用户看到可采取的下一步。

Delivery gates

按能否完成任务交付，按失败路径验收。

下面是实施次序，不是工期承诺。每一阶段都要能在真实本地仓库走通，不能用界面演示或 mock 通过代替产品验收。

第一阶段 · 技术切片

一条请求真正修改并验证代码。

配置模型、选目录、运行一个 SDK 会话，显示流式输出、工具记录和文件差异。显式工具装配与审批从第一条真实命令开始接入。

通过门槛：一个小型真实仓库中完成修改和测试；拒绝 shell 时命令未执行；关闭后恢复已保存对话。
第二阶段 · 可日常使用

任务可停止，失败可接手。

接入独立执行进程、单实例约束、sidecar、审批失效、脏文件基线和完整工作台。运行中输入仅存草稿。

通过门槛：审批时停止、命令运行时停止、重复提交、切换会话、worker 崩溃均符合契约。
第三阶段 · 首版发布

长会话与 Windows 路径都可靠。

验收压缩和重试、模型故障、存储失败、非 ASCII 目录、真实 shell 取消及界面重载。固定 SDK 版本，形成升级回归清单。

通过门槛：下面的失败场景全部通过；首次用户能独立完成任务并解释改动与验证范围。

触发场景需要观察的结果
同一 commandId 重复提交只有一个运行。重连先取快照，旧 epoch 的 submit 不会自动重放。
批准弹窗出现后点击停止等待被撤销，abort 能完成，随后点击旧“允许”不能执行工具。
SDK 自动重试或压缩UI 保持同一运行，agent_end 不提前显示完成，结束原因与验证结果分开。

Decisions & tradeoffs

有意接受的代价，留在设计里。

“简洁”来自减少重复责任，同时保留会影响用户文件和判断的必要约束。

选择换来的好处接受的代价
Pi 独占对话状态复用会话、压缩、工具循环和上游修复。遵守 SDK 会话契约；升级需要契约回归。
一个活动工作区执行进程窗口不依赖 SDK 事件循环持续响应。增加受限 IPC 和进程治理；仍需独立验证子进程取消。
当前工作目录直接编辑容易与现有编辑器和 Git 工作流配合。需要保留已有改动、承认混合归属；首版没有自动回滚。
工具串行，shell 逐次批准执行次序与授权对象容易解释。吞吐与批准便利性有限。后续按真实任务证据再优化。
sidecar 元数据，快照重连较少的存储和协议概念。与 Pi 无跨文件事务；中断时需要保守校准，而非自动续跑。
有范围的首版集中打磨修改、停止、审阅和恢复。暂不处理无人值守任务、多代理和远端执行。
设计原则如何影响了这份方案

Model the Domain 让 Workspace、Session、Run、Approval 各自承担一种责任。运行状态采用互斥分支，避免“已完成且仍在等待批准”。Prove It Works 让实际命令、文件差异和故障路径成为验收条件。本页先验收 HTML 和源码证据；应用可靠性需要实现后验证。

方案复核。 两份独立候选分别比较了 SDK 同主进程和独立执行进程。独立评审支持收窄后的执行进程方案，并要求保留最后已知快照、核对 shell 进程树、承认 sidecar 与 Pi 历史没有联合事务。最终复核补充并确认了两项修订：重启时旧命令退出未确认则保持执行锁；显式配置 SDK 工具串行，并加入验收项。

同模型家族的独立静态评审未发现剩余设计阻断项。跨家族 Kimi 审查在认证阶段失败，未产生评审结果。页面已检查桌面与手机布局、场景交互、源码检索和浏览器错误；25 处源码证据绑定本地固定提交。应用尚未实现，真实模型、命令取消与崩溃恢复仍需按发布门槛验收。
